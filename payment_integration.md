# Sales Bot WhatsApp Payment Integration Guide

This document outlines the final plan for triggering native WhatsApp payments from the `sales_bot` environment using the existing `whatsapp_interface` deployment.

## 1. No Server Changes Required for `whatsapp_interface`

**CRITICAL FINDING:** You **do not** need to rebuild, modify, or redeploy your Docker container for `whatsapp_interface` hosted on Hetzner.

**Why?**
The `send_whatsapp_order_payment` function in `whatsapp_interface` acts as a pure pass-through. It takes the `params` dictionary generated by `sales_bot` and injects it directly into the Meta Graph API payload. As long as `sales_bot` provides the mathematically correct and API-compliant JSON structure, `whatsapp_interface` will successfully deliver the native payment card to the user on WhatsApp.

---

## 2. Required Changes in `sales_bot`

To make this work, the logic in `sales_bot/core/sales_agent.py` must be updated so that the Language Model (`analysis_llm`) dynamically creates the payment parameters payload instead of returning an empty dictionary (`{}`).

### Step A: Update `SalesAgent.process_query` Return Object

In `sales_agent.py` (around line 328), the `params` field is currently hardcoded for text/audio messages:

**Current Code:**

```python
return {
    ...
    "message_type": message_type,
    "params": {}, # Hardcoded empty params
    ...
}
```

**Required Update:**
Modify the returned object to fetch the `params` generated by the LLM analysis dynamically:

```python
return {
    ...
    "message_type": message_type,
    "params": analysis.get("params", {}), # Dynamically fetched from LLM analysis
    ...
}
```

### Step B: Modify the `analysis_llm` System Prompt

To teach the agent when and how to generate the payment dictionary, you must append instructions for a "PAYMENT MESSAGE TYPE" into the system prompt that powers the `_simple_analysis` method inside `sales_agent.py`.

The Agent must be instructed to output valid JSON matching the exact Schema required by Meta's Graph API v24.0.

**Prompt Addition (Example Implementation):**

```text
8. MESSAGE TYPE DETECTION:
   - Check if the query requests voice output...
   - Check if the user wants to make a purchase, pay for a service, or requests an invoice.
   - If payment is requested, set message_type to "payment" and populate the "params" object.

Return ONLY valid JSON including the exactly formatted payment structure:
{{
  ...
  "message_type": "payment",
  "params": {{
      "reference_id": "ORD-<RANDOM_ID_HERE>",
      "retailer_id": "FOODNEST-MAIN",
      "items": [
          {{
              "name": "Service Name / Product Name",
              "quantity": 1,
              "unit_price": 50000  // Note: Price MUST be in paise! (50000 = 500 INR)
          }}
      ],
      "payment_gateway": {{
          "type": "razorpay",
          "configuration_name": "FoodNests" // The active configuration name linked in Meta Business Suite
      }},
      "currency": "INR"
  }}
}}
```

**Important considerations for the LLM Payload:**

1. **`configuration_name`:** Must be exactly `"FoodNests"` (the name of your linked Razorpay configuration in Meta Business Suite).
2. **`unit_price`:** Must be an integer representing the smallest currency unit (e.g., 100 INR is represented as `10000` paise).
3. **`reference_id`:** Must be unique for every single transaction/message sent.

## 3. Recommended Future Architecture (Dynamic Pricing)

While instructing the LLM to output the payload is the fastest integration path, Language Models can hallucinate prices.

**Best Practice:**
Create a dedicated Tool (e.g., `generate_payment_link`) that the `SalesAgent` can call. The tool would query your product database, assemble the exact `params` dictionary with 100% accurate pricing, and pass it back to the `/chat` API endpoint, bypassing the LLM's raw output.
